# Configuration

`factory_config.py` is the source of truth for repositories, labels, permissions, limits, sandbox timeout, install
commands, verification commands, and repository egress. Importing it validates the configuration.

## Render environment groups

`render.yaml` creates and links group shells. Add values in the Render Dashboard; never commit them.

### `factory-gateway`

- `RENDER_API_KEY`: scoped to starting Workflow tasks when scoped keys are available.
- `GITHUB_WEBHOOK_SECRET`: generated by the GitHub App manifest flow.
- `EVENTS_READ_TOKEN`: bearer token for the agent stream endpoints. `setup-render` generates it into `.env` when
  missing and never prints it; copy the value into this group.
- `RENDER_WORKFLOW_SLUG`: defaults in the Blueprint to `factory-workflows`.
- `DATABASE_URL`: set on the service by the Blueprint from `factory-db`, not through the group.
- `PORT`: supplied by Render. The gateway binds `0.0.0.0:$PORT`.

The gateway intentionally has no GitHub App private key and no model key.

### `factory-workflows`

- `RENDER_API_KEY`: task-run and sandbox access.
- `RENDER_WORKSPACE_ID`: workspace that owns the sandbox group.
- `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY`: App installation authentication.
- `ANTHROPIC_API_KEY`: used only by agents whose loop runs in the Workflow task.
- `FACTORY_SANDBOX_GROUP_ID`: group for all factory sandboxes and snapshots.
- `DATABASE_URL`: written by `setup-render --link-database --apply`. See [Database](#database).
- `GITHUB_API_URL`: optional GitHub Enterprise Server API base.

The Blueprint also sets `RENDER_WORKFLOW_SLUG=factory-workflows` on the Workflow service, so a Workflow task can
start another task as an independent root run.

`RENDER_ADMIN_API_KEY` is setup-only. It can be read by `setup-render`, but must never be added to either service.

The built-in agents pin `claude-sonnet-5-5` for Triage and PR Reviewer, and
`claude-opus-5-5` for Spec Writer and Implementer. Model IDs are explicit
rather than provider aliases so they remain compatible with the pinned
Pydantic AI model contract.

## Database

`factory-db` is a Render Postgres 17 database declared in `render.yaml` (`basic-256mb`, in `oregon` with the
services). It holds the append-only event log (`events`) and the tables derived from it (`runs`, `threads`,
`agent_runs`). Both services apply pending migrations themselves: Workflows on its first task, the gateway at
startup.

**Two URLs.** Render services in the same region use the internal URL, which is what the Blueprint provides. The
Blueprint sets `ipAllowList: []`, which blocks every connection from outside the workspace. To run `doctor`,
`preflight` or `db-rebuild` from a laptop, add your IP to `factory-db` in the Dashboard temporarily, and use the
external URL with certificate verification:

```text
postgresql://USER:PASSWORD@EXTERNAL-HOST/DATABASE?sslmode=verify-full&sslrootcert=system
```

The libpq bundled with psycopg-binary supports `sslrootcert=system`. Remove your IP afterwards.

**The link step.** A Blueprint can give `DATABASE_URL` to the gateway but not to a Workflow service: every sync fails
with `depends on non-existent DB`. After the Blueprint has been applied, copy the gateway's value into the
`factory-workflows` group:

```bash
RENDER_API_KEY=... RENDER_WORKSPACE_ID=... uv run setup-render --link-database          # dry run
RENDER_API_KEY=... RENDER_WORKSPACE_ID=... uv run setup-render --link-database --apply  # writes
```

It finds the single `factory-gateway` web service (Render may add a suffix), reads its `DATABASE_URL`, and upserts it
into the group. It never prints the value. Redeploy `factory-workflows` afterwards so the running service sees it.
Rerun it whenever the database is rotated or recreated. `doctor --remote` checks that the group holds the key.

**Checks.** When `DATABASE_URL` is set, `preflight` and `doctor` connect with `select 1` and list pending migrations.
Pending migrations are a warning, because the services apply them when they start. When it isn't set, the check is
skipped. Neither command prints the URL or any part of its credentials.

**`db-rebuild`.** `uv run db-rebuild` replays the event log into the derived tables. Run it after a change to
projection code that alters derived rows. It needs `DATABASE_URL` and, from a laptop, the temporary external access
above.

**Connection budget.** The gateway's pool holds up to 10 connections, and each concurrent Workflows task process up
to 3. Keep the total within the plan's connection limit; move to a larger plan, or lower the Workflows pool, before
raising Workflows concurrency.

## Sandbox credential broker

Credential brokering is optional. `factory_config.py` controls it with:

```python
SandboxSettings(brokered_model_access=False)
```

With the default `False`, every model loop runs in the Workflow task and only its tools execute in the sandbox.
The provider key remains confined to Workflow compute, and provider egress is omitted from every sandbox.

Set it to `True` only after `doctor --remote --probe-brokering` passes. Implementer and PR Reviewer then use their
declared in-sandbox placement.

The intended Anthropic credential is attached to the factory sandbox group with:

- exact domain `api.anthropic.com`
- header `x-api-key`
- method `POST`
- path `/v1/messages`

`setup-render --apply-credential` configures this through the pinned SDK's generated API. The operation requires
an enabled workspace and an authorized setup key. `doctor --remote` verifies the non-secret domain, method, path,
and injection metadata. Do not replace brokering by copying `ANTHROPIC_API_KEY` into a sandbox.

## Local files

`.env.example` documents every key. A populated `.env` is ignored by git. `preflight --env-file PATH` and
`doctor --env-file PATH` read it without printing values. `setup-render --env-file PATH` adds a generated
`EVENTS_READ_TOKEN` to it (mode 0600) when it has none.
